# 設計段階の検討シート

2026-11-05 時点

アプリ開発で使われる「要件定義書（PRD：プロダクト要求仕様書）」の形式で、作り始める前に決めることを並べたシートです。各表の「決めた内容」の列に書き込んで使います。上から順に決めると、後の項目の判断がぶれにくくなります。

## 1. 概要

最初に、アプリを一文で言えるようにします。ここが決まらないと、後の項目すべてがぶれます。

| 決めること | 考えるための問い | 決めた内容 |
| --- | --- | --- |
| アプリの一文説明 | 「〇〇な人が、〇〇のときに、〇〇できるアプリ」と言えるか | 数学を学びたい人が、試験や受験の勉強のとき、解法を選択する方法を身に付けるアプリ |
| 解決したい課題 | 学習者はいま何に困っているか。それは今ある教材や授業で解決できていないか | 数学において問題と解答の1対1対応で学習しており、応用的な思考が身に付いていないとき。問題文から何を連想するかを覚えて、初見の問題にも対応できる応用力と柔軟性を身に付ける。 |
| 目的（ゴール） | 使い終わった学習者は、何ができるようになっているか | 初見の問題や応用問題において解法を選べる。道筋を立てられる。完答はできなくても途中までは解ける。問題文を見てまったく何もわからないという状態から抜け出せる。 |
| やらないこと | このアプリが目指さないことは何か（例：解答を教える、問題集の代わりになる） | |
| 作る理由 | 自分が作る意味は何か。授業・教材作りの経験のどこが活きるか | 授業において使用。学生の自習において使用。 |

## 2. 利用者と利用場面

利用者を一人の具体的な人物（ペルソナ）として描き、使う場面を場所・時間・端末まで決めます。

| 決めること | 考えるための問い | 決めた内容 |
| --- | --- | --- |
| 主な利用者 | 学年・成績層・目標（定期テスト、共通テスト、二次試験）はどこか | 中学生～高校生。 |
| その人のつまずき | 解けないとき、どこで止まっているか（読み取り、方針、計算、忘れている公式） | 問題文を見てどのように解くかわからない。授業はわかるが問題が解けない。解答を見たら理解できるがいざ解くとわからない。 |
| 使う場面 | 家での復習か、授業中か、自習室か。1回何分か | 家での学習、授業中。1問10～30分想定。 |
| 使う端末 | スマホ・PC・VRグラスのどれが主か。VRグラスは利用者が実際に持っているか | スマホ、ＰＣ、vrグラスで利用できるようにする。使用感がかわるのでｖｒグラスは仕組みを変えて他２つとは別で作る。 |
| その他の関係者 | 先生（課題を出す、進みを見る）や保護者が使う画面は必要か | 他の利用者との勉強時間で競う仕組みあり。 |
| 問題を作る人 | 問題データは誰が作るか（自分だけ、先生たち、AI） | 先生が作成。AIが作成。また、教科書や問題プリントを読み込んでＡＩがそれ用のヒデータを作る自作問題も作りたい。 |

## 3. 価値と差別化

前回の設計で弱かった「新規性」と「VRで使う理由」を、ここで言葉にします。答えられない項目があれば、それが最初に詰める問題です。

| 決めること | 考えるための問い | 決めた内容 |
| --- | --- | --- |
| 代わりになるもの | 学習者はいま何でこの課題を解決しているか（参考書の解説、映像授業、先生に質問、AIチャット） | 先生に各自で聞いている。ＡＩに聞いている。youtubeや塾での詳細な解説動画で確認。 |
| それらでは足りない点 | 代わりになるものの何が不満か。このアプリはそのどこを埋めるか | 先生のレベルによって得られるレベルも変わってしまう。先生の対応時間が限られるため、全員に提供ができない。ＡＩも解答は出してくれるが、「問題文のどの部分からどのように考える」というのは"聞かないと"教えてくれない。映像では個別最適化ができない。授業や問題の解説文では確認しにくい部分のため、そこでは得られない知識。 |
| 新規性 | このアプリにしかない体験は何か。一文で言えるか | 「問題文からの連想とそれらの組み合わせでさらに何を連想するか」といった問題を解く際の思考の言語化や透明化を見られる。思考の後に解答が出来上がるが、解答に書かれない部分の思考を視認できる。 |
| VRで使う理由 | 画面ではできず、空間だからできることは何か（広い作業面、手の動きでの操作、立体の図形、周りが見えない集中など） | スマホやＰＣではノートを書く作業が同時にできない。またＶＲグラスであれば書いた内容も取り込めるため、それをＡＩが読み込んで方針が立てられる。 |
| VRなしでも成り立つか | スマホ・PCだけの利用者にも価値があるか。VRは必須か、より良くなる選択肢か | スマホＰＣだけでももちろん可能。視点がノートと端末画面に行き来する不便さ、書いた内容が自動で取り込まれないことで使えない機能が生まれるが、基本機能は使える設計。 |

## 4. 学習体験の設計

学習者が1問に取り組む間に、何を見て、何をして、何が返ってくるかを決めます。「分かり切ったヒントを何度も見るわずらわしさ」は、ここの「ヒントの出し方」で解消します。

| 決めること | 考えるための問い | 決めた内容 |
| --- | --- | --- |
| 中心となる体験 | 1問の流れを、始めから終わりまで5手順程度で書けるか | 問題文から何を発想するか、連想するか、気づくべきか、注意すべきかという思考プロセスを見ることができる。 |
| 学習者がすること | 見るだけか、自分で選ぶ・書く・並べるなどの操作をするか | 操作する。次のヒントを見るときなどに触ることがある。 |
| ヒントを出すきっかけ | 学習者が求めたときだけか、つまずいたときだけか、決まった順番か | 少なくとも決まった順は避けたい。理解している内容を出されると煩わしく感じるため。利用者のレベルに合わせて、または求めに応じて適切なものを表示したい。方法を模索中。 |
| ヒントを飛ばす仕組み | 分かっていることをどう判断するか（自己申告、先に答えさせる、過去の結果） | 模索中。 |
| ヒントの段階 | 一度に答えを見せず、どう段階を踏むか（どこを見るか → 何が言えるか → どう使うかなど） | 模索中。 |
| 正誤の返し方 | 学習者の選択・答えに、何を返すか。間違えたときに理由を示すか | 正誤は入力しないので返さない。 |
| 繰り返しと定着 | 同じ型の問題をどう繰り返させるか。得意なものは飛ばすか | くりかえすかどうかは利用者判断。自動出題はしない。 |
| 1回の長さ | 1問・1回の利用は何分を想定するか（VRは長時間だと疲れる） | 1問は難易度によって変わる。1回の利用を1時間程度とする。ただし、もっと利用したい場合に制限するものではない。 |

## 5. 機能要件

機能を書き出し、MoSCoW（モスコウ）という分け方で優先度を付けます。最初の版では「必須」だけを作ります。

| 区分 | 意味 | 入れる機能 |
| --- | --- | --- |
| Must（必須） | これがないと中心となる体験が成り立たない | 手動問題作成機能（教師が作成する）。作成された問題から思考を視覚化する。利用者がアップした問題から問題データを作成する（ＡＩ機能）。ヒントなどを保存する空間、そこでヒント同士の関連性表示。くっつけると別の思考に代わるなどの思考強化機能。 |
| Should（できれば） | 大事だが、なくても試してもらえる | 利用者の解答を読み込んで、次に見るべき部分、そこからの思考をリアルタイムで（利用者が指示を出したら即時）表示する。自習時間の記録と他ユーザーとの競い合い機能。 |
| Could（あれば良い） | 余裕があれば作る | 別解や高難易度の問題。aiとチャットしながら解くモード。 |
| Won't（今回はやらない） | やらないと決めたもの。書いておくと議論が戻らない | |

各機能については、「誰が、何をしたいときに、何ができる」の形（ユーザーストーリー）で一文ずつ書くと、必要かどうかを判断しやすくなります。例：「解き方の見当がつかない生徒が、問題文のどこを見ればよいかだけを知りたいときに、答えを見ずに手がかりだけを得られる」。

## 6. コンテンツとデータ

学習アプリは問題データの量と質で価値が決まります。作る手間が現実的かもここで確かめます。

| 決めること | 考えるための問い | 決めた内容 |
| --- | --- | --- |
| 扱う範囲 | 科目・単元・難易度はどこから始めるか。最初は1単元に絞るか | 数学の高校生の内容（数学ⅠＡ、ⅡＢ、ⅢＣ）<br>青チャートのレベルまで |
| 問題の入手 | 問題はどう用意するか（自作、問題集を参考にした類題）。著作権に問題はないか | 問題集の類問、自作 |
| 1問あたりの中身 | 1問に何を用意するか（問題文、ヒント、解答、図、よくある間違い） | 問題文、問題文の一部分、それから連想すること（１～３つ）、思考する内容 |
| 1問を作る手間 | 1問作るのに何分かかるか。目標の問題数を作り切れるか | |
| AIの使い方 | AIに下書きさせるか。人が確かめる手順をどうするか | ＡＩにも作らせる。最終チェックは人。 |
| 数式・図の表し方 | 分数・根号・グラフ・図形をどう表示するか（文字だけで足りるか） | Latexが理想。 |
| 学習記録 | 何を記録するか。端末の中だけか、サーバーに保存するか（個人情報の扱い） | ユーザー名と勉強時間。サーバーに保存したい。 |

## 7. 非機能要件

機能以外の「どれだけ快適・確実に使えるか」を決めます。技術選定の前提になります。

| 決めること | 考えるための問い | 決めた内容 |
| --- | --- | --- |
| 対応端末 | どの端末で動かすか（Quest、Android XR、iPhone、Android、PC）。優先順は | Android XR、iPhone、Android、PC |
| 通信 | 通信がない場所でも使える必要があるか | 使える方が良い。使えない機能があるのは構わないが、内蔵された問題は通信環境なしでも使えるようにする。 |
| 快適さ | 起動に何秒まで許すか。VRで酔わないための条件（滑らかさ、動きの少なさ）は | 勉強に支障を与えない程度に早く起動して欲しい。 |
| 使いやすさ | 文字の大きさ、色の見分け、音声、片手操作など、配慮することは | 文字の大きさやフォントは日本人ユーザーの一般的な視認性に合わせて作成。 |
| 個人情報 | 生徒の情報を扱うか。扱うなら、学校のルールに合うか | 扱わない |
| 費用 | 公開・運用に毎月いくらまでかけられるか（無料の範囲に収めるか） | 最初のモデル作成までは無料の範囲で基本的に実施する。アプリの有料販売に向けて作成する段階になったら、サーバー用への課金を検討する。 |
| 利用料 | 利用者から料金をとるか。とるならいつから、いくらか | 取る予定。まずは無料版作成予定。買い切り、または、ＡＩ利用、問題集増加といった機能ごとに月額課金という形も検討の余地あり。 |

## 8. 技術選定

技術は1〜7が決まってから選びます。先に技術を決めると、体験が技術のできることに引っ張られます。

| 決めること | 考えるための問い | 決めた内容 |
| --- | --- | --- |
| アプリの形 | ウェブアプリ（WebXR）か、ストアで配るアプリ（Unityなど）か | 未定 |
| 表示の仕組み | 3Dの描画に何を使うか（three.js、Babylon.js、Unity）。画面版とVR版で共通にできるか | 未定 |
| 操作の入力 | コントローラー、手の認識、視線、音声のどれを使うか | 未定 |
| サーバー | サーバーが必要か（学習記録の保存、AIの利用、ログイン） | 競い合いの部分でユーザー情報は使用予定。ただし、競い合い機能は今後なので優先順位低め。 |
| 公開方法 | GitHub Pages、ストア（Meta Horizon Store、Google Play）のどれで配るか。登録料は | 未定 |
| 開発の進め方 | Claude Codeの設定（CLAUDE.md、Rules、Skills、Hooks）を最初にどこまで用意するか | 開発効率を考えて利用するものを検討。CLAUDE.mdはマスト。その他は検討。 |

## 9. 成功指標と検証

「うまくいった」を何で判断するかを、作る前に決めます。決めておくと、今回のような「思っていたものと違う」に早く気づけます。

| 決めること | 考えるための問い | 決めた内容 |
| --- | --- | --- |
| 学習の成果 | 使った生徒の何が変われば成功か（初見の問題で方針を立てられる、着眼点を言える） | |
| 使われ方 | 続けて使ってもらえているかを何で見るか（繰り返し使う人数、1回の利用時間） | |
| 満足度 | 学習者に何を聞くか（わずらわしさ、分かりやすさ、VRで使いたいか） | |
| 試す方法 | 作り込む前に、紙の試作や操作できる画面の試作（プロトタイプ）で誰に試してもらうか | |
| 作り直しの基準 | 試した結果がどうなら、設計を見直すか | |

## 10. スコープと進め方

最初の版（MVP：中心となる体験を確かめるための最小の版）を小さく決め、試してから広げます。

| 段階 | 内容 | 確かめること | 目安の時期 |
| --- | --- | --- | --- |
| 0. 設計 | このシートを埋める | 1〜3章を一文ずつ言えるか | |
| 1. 試作 | 紙や画面の試作で1問だけ体験する | 中心となる体験が面白いか、わずらわしくないか | |
| 2. MVP | Must の機能だけで1単元を作る | 生徒が続けて使うか、9章の指標 | |
| 3. VR対応 | VRでの体験を加える | VRのほうが良いと言えるか | |
| 4. 拡張 | 単元・問題数、Should の機能を増やす | 問題を作る手間が回るか | |

VRをどの段階で入れるかは、3章の「VRで使う理由」次第です。VRにしかない体験が中心なら、段階1からVRで試します。

## 11. リスク・前提・未決事項

決めきれないことは、空欄にせずここに書いておきます。作り始めてから判断がぶれるのを防げます。

| 区分 | 書くこと | 内容 |
| --- | --- | --- |
| 前提 | 正しいと仮定していること（例：生徒はVRグラスを使える） | |
| リスク | うまくいかないかもしれないことと、そのときの対応（例：問題を作る手間が足りない → 単元を絞る） | |
| 未決事項 | まだ決めていないことと、決める期限・決め方 | |
| 参考にするもの | 似たアプリ、教材、授業の工夫など | |

- [ ] 9章の成功指標を決めた
- [ ] 新しいリポジトリを作る
